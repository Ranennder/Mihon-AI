# Аудит Mihon AI — 21 сентября 2026

Проверена база `e91421267` (`v0.1.22`), изменения подключения и AI в `v0.1.14–v0.1.22`, обновление Mihon до `0.20.4`, установка расширений и повторная загрузка страниц. Приложение на Kotlin/Compose связано с Python-компаньоном, который запускает Real-ESRGAN. Интернет-доступ использует временный Cloudflare Quick Tunnel.

Причины ниже подтверждены кодом и регрессионными проверками. Без журналов телефона нельзя утверждать, что каждая проявилась именно в пользовательском случае.

## 1. Доступ вне локальной сети

- Сохранённый LAN-адрес возвращался даже после неудачной проверки связи. Ручной локальный адрес также препятствовал переходу на туннель в другой Wi-Fi сети. Исправлен выбор адреса; выключенный интернет-режим не использует старый туннель. Ручной публичный сервер сохраняет приоритет.
- `internet_url: null` мог сохраняться как строка `"null"`. Теперь принимается только корректный HTTPS URL.
- Переключатель лишь сохранял настройку. Теперь открытые AI-настройки запускают сопряжение и показывают результат или ошибку.
- Компаньон считал туннель готовым при появлении URL в стартовом выводе. Теперь ожидается регистрация соединения, ошибки сохраняются, завершение процесса сбрасывает адрес.
- Выбран HTTP/2: Quick Tunnel без указанного протокола использовал QUIC, что мешало работе при блокировке UDP. Это подтверждается [исходниками cloudflared](https://github.com/cloudflare/cloudflared/blob/master/cmd/cloudflared/tunnel/quick_tunnel.go).
- Одиночная отправка на HTTPS-сервер использует асинхронную задачу. Длительная обработка GPU не удерживает один запрос без ответа, устраняя соответствующий риск [Cloudflare 524](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/).

После перезапуска компаньона требуется повторное сопряжение в одной Wi-Fi сети: временный адрес меняется. Обнаружение нового адреса из мобильной сети этим решением не реализовано.

## 2. Прямая загрузка на ПК

- Загрузчик и держатели страниц скачивали оригинал телефоном до прямого AI-запроса. Теперь оригинал загружается только при необходимости; успех прямой обработки или AI-кэш не требуют оригинала.
- Переключатель был доступен только для целой главы, хотя `v0.1.22` добавила одиночные страницы. Теперь доступен во всех режимах.
- Терялись явный Cookie и сессия отдельного клиента расширения. Сохранены cookies источника и User-Agent. Запрашивается несжатое HTTP-тело: urllib сам не распаковывает gzip/Brotli.
- Исправлено сообщение об ошибке, вызывавшее отсутствующий метод сервера, и повтор временных ошибок опроса.
- Если принятая задача прямой загрузки главы позднее падает, оставшиеся страницы один раз загружаются через телефон; уже готовые сохраняются. Повторное использование серверной задачи проверяет индексы и содержимое страниц, чтобы разные изображения не получали один и тот же результат.

Расширения с собственными перехватчиками или преобразованием изображений могут требовать запасной загрузки через телефон. Она использует HTTP-клиент самого расширения. Сохранение, отправка и установка обложки тоже могут потребовать оригинал.

## 3. Расширение снова предлагает обновление

- Для повторяющегося пакета проверка обновления брала первую запись репозитория, скачивание — последнюю. Могла повторно ставиться старая версия. Теперь обе операции используют одну выбранную версию.
- После успешной установки установленная версия читается заново, индикатор обновления пересчитывается, без зависимости только от Android package broadcast.
- Исправлены неатомарные изменения списков и отмена чужой установки. Попытки имеют разные ID и файлы; завершение старой попытки не удаляет новую.

Эти дефекты существовали до `b81bc6d60`: обновление базы напрямую установщик не меняло. Причина именно пользовательского случая без журналов и списка репозиториев не установлена.

## 4. Перезагрузка картинки при сбое AI

- Ошибка AI оставляла исходную страницу в состоянии `Ready`. Кнопка отправляла её в обычную очередь, которая принимает только `Queue`, поэтому ничего не происходило.
- Теперь повторная попытка очищает AI-результат и запускает обработку заново. Старый ответ фоновой главы не может перезаписать результат повторной попытки.
- Для ошибок оригинала восстановлена принудительная загрузка. Ошибка фоновой главы отображается вместо бесконечного ожидания; отмена coroutine не запускает новую загрузку.

## Дополнение для v0.1.24

Пользователь подтвердил повторное предложение обновлений в v0.1.23 и старую версию AllHentai в настройках Android. Проверены текущие APK девяти расширений со скриншота: версии соответствуют каталогу Keiyoushi, а необходимые классы и методы присутствуют в опубликованном APK v0.1.23. Несовместимость API или формата каталога этим случаем не подтверждается. Точный установщик и сохранённый URL пользовательского хранилища пока неизвестны.

- В LEGACY-установщике отсутствовала очередь: массовая загрузка открывала несколько системных окон установки одновременно. Это воспроизведено на опубликованной v0.1.23 в Android 15: два `ExtensionInstallActivity` и два `PackageInstallerActivity` после одного Update all. Теперь подтверждения открываются последовательно. Тестовые APK имели реальные DEX расширений, изменённые версии в manifest и отдельную временную подпись; историческую совместимость ABI этот сценарий не проверяет.
- APK обновления сверяется с ожидаемым именем пакета и versionCode до установки; после системного результата проверяется действительно загруженная версия. Ошибка загрузки или оставшаяся старая версия больше не выдаются за успешное обновление. Обновление списка перечитывает ожидающие обновления пакеты.
- Сохранённые адреса хранилищ обновляются перед ручным запросом списка. Это учитывает переход Keiyoushi с legacy-индекса на `index.pb`, описанный в [официальном репозитории](https://github.com/keiyoushi/extensions-source/issues/18072).
- При пересоздании Android activity повторное окно не открывается и APK не удаляется преждевременно. Ошибка запуска системного установщика завершает попытку и освобождает очередь.
- В Windows воспроизведена маскировка ошибки занятого порта: `server_close()` обращался к ещё не созданным полям. Исправлены очистка, определение владельца порта через WinAPI, исключительное владение сокетом и завершение прежней копии до автообновления. Проверка принадлежности процесса учитывает адрес конкретного listener, а перезапуск PyInstaller получает независимое окружение и сохраняет аргументы с пробелами/Unicode.
- Windows CI проверяет передачу порта между двумя Python-процессами и между двумя собранными EXE, включая завершение родительского процесса PyInstaller.

После восстановления сервера `spotlessCheck` и все **113 JVM-тестов** прошли без ошибок и пропусков. На Linux прошли **30 Python-тестов**, ещё три требуют Windows; для них предусмотрены проверки в Windows CI. Незавершённые во время зависания локальные APK не используются для релиза.

Windows CI затем успешно выполнил проверки исходного компаньона, передачу аргументов через PowerShell и отдельный тест передачи порта между двумя собранными EXE. Таким образом, Windows-сценарии проверены на настоящем Windows runner, а не только с подменой WinAPI на Linux.

### Сбой рабочего сервера

Во время одновременной полной сборки и работы Android-эмулятора журнал сервера зафиксировал memory pressure в 19:41–19:42. После зависания сервер перезапущен в 20:04; файлы изменений сохранились, временные логи и незавершённые APK не считаются результатом успешной проверки. Прямой записи OOM-kill в сохранившемся журнале нет, но совмещённая нагрузка является вероятной причиной нехватки памяти.

Для продолжения введён `scripts/gradle-local.sh`: cgroup ограничивает всё дерево сборки 4 GiB памяти и 1.5 CPU, Gradle использует два worker и один JVM для компиляции Kotlin. `AGENTS.md` запрещает совмещать Gradle и эмулятор на этом сервере; релизные сборки выполняются в GitHub Actions. Логи последующих проверок сохраняются вне `/tmp`.

Дополнительно файловая блокировка исключает одновременные запуски локального Gradle. Проверены обычный запуск wrapper и отказ второго запуска с кодом 75. После завершения проверки сервис сеанса отвечал за 0.02–0.05 секунды, доступно около 9 GiB памяти, текущий memory pressure равен нулю.

## Повторный отказ обновлений после v0.1.24

Пользователь подтвердил: одиночное обновление открывает окно Android, после согласия окно закрывается, установленная версия остаётся прежней. На ранее присланном скриншоте круглая стрелка соответствует `InstallStep.Error` (повтору после ошибки). Причина ошибки в интерфейсе отсутствовала. Это не доказывает несовместимость версии приложения или кэша каталога.

- Legacy-установщик терял возвращаемый Android код `android.intent.extra.INSTALL_RESULT`. PackageInstaller и Shizuku не передавали текст отказа экрану расширений. Теперь ошибка сохраняется, попадает в журнал и показывается в диалоге с копированием.
- Обход раннего ложного callback MIUI теперь применяется только к отмене без native-результата. Явная ошибка или успешный результат больше не теряются в первую секунду.
- Перед системным обновлением сравниваются сертификаты установленного и скачанного APK. Подтверждённый конфликт разных ключей получает объяснение с ручной переустановкой только расширения. При истории ротации ключей, недоступных данных или ошибке чтения решение остаётся за Android. Автоматического удаления нет.
- Подпись AllHentai 1.6.68 из текущего Keiyoushi — SHA-256 `9add655a78e96c4ec7a53ef89dccb557cb5d767489fac5e785d671a5a75d4da2`, minSdk 26, targetSdk 37. Подпись установленной пользовательской 1.4.65 неизвестна. Аналогичный отказ из-за разных ключей описан в [Keiyoushi #9198](https://github.com/keiyoushi/extensions-source/issues/9198#issuecomment-2968025197), но для этого телефона причина пока не установлена.

Эти изменения исправляют скрытие ошибок и позволяют получить конкретную причину; успешная установка на пользовательском телефоне ещё не подтверждена.

Локально через `scripts/gradle-local.sh` прошли все **78 тестов модуля app**, в том числе 26 новых проверок сохранения ошибки, сравнения сертификатов, результата Legacy/MIUI и отмены/повтора во время проверки установленной версии. Эмулятор не запускался. Лог: `~/.cache/mihon-ai-validation/extension-diagnostics-tests.log`.

### Причина AllHentai подтверждена на телефоне

После выпуска v0.1.25 пользователь указал выбранный установщик **PackageInstaller** и прислал результат проверки сертификатов:

- Установленный AllHentai: SHA-256 `cbec121aa82ebb02aaa73806992e0368a97d47b5451ed6524816d03084c45905`.
- Скачанное обновление: SHA-256 `9add655a78e96c4ec7a53ef89dccb557cb5d767489fac5e785d671a5a75d4da2`, совпадает с проверенным официальным APK Keiyoushi.

Для AllHentai причина установлена: разные подписи препятствуют системному обновлению поверх старого APK. Требуется однократное удаление **только расширения AllHentai** и установка его версии из Keiyoushi. [Официальная инструкция Keiyoushi](https://keiyoushi.github.io/docs/guides/troubleshooting#extension-installation-issues) описывает этот случай и подтверждает сохранность библиотеки и настроек расширений. Источник старого APK и причины отказов остальных расширений по одному сертификату не определяются. Успешная переустановка на телефоне пока не подтверждена.

Оба workflow v0.1.25 завершились успешно: Release `35638003084`, Build & Test `35638001840`; в CI прошли **139 JVM-тестов**. Опубликованный APK имеет versionCode `7763` и прежнюю подпись приложения.

## v0.1.26: переустановка расширения из приложения

Пользователь запросил автоматизацию удаления старого расширения и согласился на системное подтверждение Android. Добавлена кнопка «Переустановить» для конкретного расширения с подтверждённым конфликтом подписей. Обычное обновление само удаление не запускает.

- Новый APK сначала полностью скачивается в отдельный внутренний каталог приложения. До удаления проверяются пакет, версия, сертификат выбранного хранилища, минимальный Android SDK, признак расширения и поддерживаемая версия API расширений.
- Затем отдельная Activity запускает системное подтверждение удаления только этого пакета. После подтверждения проверяет фактическое отсутствие старого пакета, повторно проверяет APK и запускает выбранный установщик.
- Отмена удаления сохраняет старое расширение. Отменённые и заменённые попытки не могут продолжить установку по позднему callback. Пересоздание Activity не повторяет запрос удаления; файл не удаляется при повороте экрана.
- Библиотека, история, прогресс и настройки источников Mihon не очищаются. Разные подписи не обходятся: старый APK удаляется через Android с согласием пользователя.
- Передача APK через FileProvider ограничена отдельным внутренним каталогом. Проверки не загружают код скачанного расширения.

Для обычного PackageInstaller Android требует подтверждения пользователя; полностью скрытое удаление в этот сценарий не входит.

Локально прошли `spotlessApply`, **117 тестов app** и `assembleDebug` через ограниченный `scripts/gradle-local.sh`. После компиляции добавлена отправка отмены восстановленного `downloadId` в очередь системного установщика и соответствующая проверка в тесте. Финальный коммит `f99514ce2998eb67bc8a2bb1383d117d9bac9a9a` успешно прошёл [Build & Test 35642984462](https://github.com/Ranennder/Mihon-AI/actions/runs/35642984462): форматирование, релизная сборка и **178 JVM-тестов** без пропусков и ошибок, включая новую проверку отмены. Windows: 32 теста исходников прошли, 1 пропущен; отдельный тест передачи управления между запусками готового EXE прошёл. Эмулятор запускался только после завершения Gradle, с лимитом 3 GiB / 1 CPU и общим lock со сборкой.
